## Documentation impact

### 1. Inferred PDF field mappings ([#207](https://github.com/LemmaLegalConsulting/docassemble-WorkflowDocs/pull/207))

Workflow Docs no longer requires every interactive PDF to have a non-empty sidecar `fields` mapping. For unmapped PDF fields, v1.5.7 can infer values from AssemblyLine/ALWeaver-compatible labels. Explicit sidecar entries still take precedence.

Important behavior to document:

- Inference applies to both predefined and computer-uploaded PDFs.
- Uploaded PDFs may now be accompanied by same-upload `.yml` sidecars. Matching uses the exact, case-sensitive filename stem; orphan, duplicate, or malformed sidecars are rejected.
- One-based person-list labels are translated to Docassemble paths, for example:
  - `clients1_name_first` → `clients[0].name.first`
  - `clients2_signature` → `clients[1].signature`
  - `client_signature` → `clients[0].signature`
  - `advocates1_signature` → `advocates[0].signature`
  - `advocate_signature` → `advocate.signature`
  - `users1_address_block` → `users[0].address.block()`
- Recognized person signature labels are the only inferred fields automatically routed as TemplateRequests. Ordinary inferred fields resolve directly.
- Explicit sidecar entries, including `request: false`, override inference for that physical field.
- Repeated `__N` labels and paired boolean labels such as `is_minor_yes` / `is_minor_no` follow AssemblyLine conventions.
- The exact generic label `signature` is intentionally left blank rather than routed; unsupported labels, Unicode/spaces/punctuation, Python keywords, and invalid zero indexes remain unmapped unless explicitly configured.
- Flat PDFs with no interactive fields pass through unchanged.
- Advocates can open **Review PDF field mappings** under the selected-template list. It reports explicit, inferred, DACatchAll, and unmapped fields; target expressions; stale sidecar entries; and per-PDF counts. Requestees do not see this review.
- PDF requestee visibility now applies to explicit and inferred requested fields for predefined and uploaded PDFs.
- When one PDF field requests a variable and another derives from the same variable, non-final passes do not independently gather the derived field.

Current documentation conflicts with v1.5.7 in several places: `docs/pdf-templates.md`, `docs/template-author-guide.md`, `docs/template-actions.md`, and `docs/assemble-documents.md` say or imply that a PDF sidecar is required, inference does not occur, or PDF electronic request routing is unsupported.

### 2. Template tool link visibility ([#208](https://github.com/LemmaLegalConsulting/docassemble-WorkflowDocs/pull/208))

The release:

- Shows **Manage templates** in the Assemble Documents interview only to users with `manage_templates`, `admin`, or `developer` privileges.
- Applies the same privilege gate to the Template Manager link on the sign-in screen.
- Adds per-client `show docx labeler link`, defaulting to `true`. Setting it to `false` hides **Template builder** from Assemble Documents.
- Does not replace the labeler's own authentication and privilege checks; hiding the link is presentation/configuration, not the security boundary.

Current documentation lists both tools but does not describe where their links appear, the privilege gate, or the new setting.

## Recommended edits

### Priority 1 — Add v1.5.7 to What’s New

**File: `src/pages/whats-new.md`**

Add `Version 1.5.7 — September 7, 2026` above v1.5.6 with two concise audience-facing sections:

1. **Faster setup for fillable PDFs** — explain that compatible PDF field labels can map automatically, optional sidecars can override behavior, and advocates can review mappings before proceeding. Link to `/docs/pdf-templates` and `/docs/assemble-documents`.
2. **More control over template-tool links** — explain that template-management links respect privileges and administrators can hide the DOCX Template Builder link per organization. Link to `/docs/admin-guide` and `/docs/template-author-guide`.

Do not expose internal parser class names, DACatchAll implementation details, formatting-only commits, or issue-specific test names on the release page.

### Priority 2 — Rewrite the PDF guide’s setup model

**File: `docs/pdf-templates.md`**

This is the main v1.5.7 update.

1. Revise the introduction and quick start:
   - A fillable AcroForm PDF is required.
   - A YAML sidecar is optional when compatible field names provide enough mapping.
   - Sidecars remain the mechanism for explicit variables, questions, conditions, formatting, request overrides, and final actions.
2. Add an **Inferred field mappings** section with a compact label-to-target table and explain one-based list labels.
3. Clearly separate:
   - inferred ordinary fields;
   - inferred person signatures, which become external requests in electronic mode;
   - generic valid variable names that use ordinary lookup and may become DACatchAll;
   - unmapped/invalid labels that remain blank.
4. Document precedence: explicit sidecar mapping wins, including explicit blanks and `request: false`.
5. Document supported repeated and yes/no label conventions and the intentionally unmapped exact `signature` label.
6. Add **Review PDF field mappings** guidance: who sees it, where it appears, statuses shown, stale sidecar entries, and how authors should resolve unmapped fields.
7. Add uploaded-sidecar instructions and exact matching/validation behavior.
8. Update “How PDF assembly works,” render-pass notes, requestee visibility, troubleshooting, and authoring checklist to cover inferred and explicit mappings together.
9. Remove or rewrite every obsolete claim that a predefined PDF requires a non-empty sidecar or that Workflow Docs does not infer mappings.
10. Preserve the detailed sidecar reference; inference supplements rather than replaces explicit mappings.

Suggested examples should include `clients1_name_first`, `clients2_signature`, `advocate_signature`, `users1_address_block`, a repeated `__2` field, and a paired yes/no field. Include a warning against zero-based labels such as `clients0_signature`.

### Priority 3 — Correct the Assemble Documents workflow

**File: `docs/assemble-documents.md`**

1. Update the opening paragraph and signature-request section: PDFs can participate in electronic request routing when a sidecar explicitly requests a field or a compatible person-signature label is inferred.
2. Update computer upload instructions to include `.yml` sidecars and explain exact same-stem matching.
3. Mention the optional **Review PDF field mappings** link after PDF selection and link to the PDF guide.
4. Clarify that the **Manage templates** shortcut appears only for `manage_templates`, `admin`, or `developer`; the **Template builder** shortcut may be hidden by organization configuration.
5. Retain existing DOCX `| request` guidance, but stop presenting it as the only route to electronic requests.

### Priority 4 — Update author and actions cross-references

**Files:**

- `docs/template-author-guide.md`
- `docs/template-actions.md`

For `docs/template-author-guide.md`:

- Explain that compatible PDF labels can map automatically and that a sidecar is optional unless the author needs explicit overrides or advanced behavior.
- Describe the mapping-review link as the author’s verification tool.
- Clarify Template Manager privilege requirements and configurable visibility of the Template Builder shortcut.

For `docs/template-actions.md`:

- Replace any statement that a PDF sidecar necessarily contains a required field mapping.
- Explain that a sidecar may contain `fields`, `actions`, or both; inferred fields can coexist with explicit `fields` and `actions`.

### Priority 5 — Add administrator configuration

**File: `docs/admin-guide.md`**

1. Add `show docx labeler link` to the per-client key table:
   - default `True`;
   - `False` hides **Template builder** in Assemble Documents.
2. Add it to the complete YAML example.
3. In System Tools/permissions, distinguish:
   - Template Manager shortcut visibility requires `manage_templates`, `admin`, or `developer`;
   - Template Builder shortcut visibility is controlled by the client setting;
   - direct access remains protected by the tools’ authentication/privilege checks.
4. Avoid describing link hiding as an authorization mechanism.

- `docs/request-filter.md`: DOCX/Jinja `request` behavior remains valid.
- `docs/send-questionnaire.md` and `docs/request-documents.md`: v1.5.7 does not change these workflows.
- The v1.5.6 release entry: its features were genuinely released in v1.5.6 and should not be relabeled.
- `plans/v1.5.6-documentation-update-plan.md`: retain as historical planning context; add this separate v1.5.7 plan instead of rewriting history.

## Definition of done

- v1.5.7 is the newest release on What’s New and links to detailed guidance.
- The PDF guide accurately teaches both inferred and explicit mappings for predefined and uploaded PDFs.
- No documentation says a PDF sidecar is always required or that PDFs cannot use electronic request routing.
- Authors can understand the mapping review statuses, precedence rules, and unmapped-field remedies.
- Administrators can configure `show docx labeler link` and understand the difference between link visibility and authorization.
- The site typechecks and builds successfully with no stale contradictory claims.
